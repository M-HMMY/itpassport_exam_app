# 章を書かせるときのプロンプト

教本の各章は、ここに置いたプロンプトを Codex CLI に渡して書かせました。**残りの章や確認問題を足すときも、この形をひな形にしてください。**

## 使い方

```bash
codex exec --cd "C:\Dev\itpassport_exam_app" --sandbox workspace-write --color never \
  -o out.txt - < scripts/prompts/03-tech-sec.md
```

- `--sandbox workspace-write` … このリポジトリの中だけ書き換えを許す
- `-o out.txt` … **最終メッセージだけ**をファイルに落とす。途中の思考ログを読まずに済むので、依頼した側のコンテキストを食わない
- `-` … プロンプトを標準入力から読む（長い日本語をシェルの引用符で壊さないため）

複数を同時に走らせられます。**ただし 1 ファイル 1 担当**にしてください。教本を `src/data/textbook/` の下で「まとめて書く単位」ごとに分けてあるのはこのためです。

## プロンプトに必ず入れること

実際に効いた要素です。省くと品質が落ちます。

1. **読むファイルの指定** … `CLAUDE.md`、`src/data/categories.ts` の該当章、すでに完成した章（文体の見本）
2. **書くファイルの限定** … 「他のファイルは絶対に変更しないでください」。同時に走っている担当も明記する
3. **節の一覧を表で渡す** … id・タイトル・内容の目安。id を決めて渡さないと勝手な id を作ります
4. **読者像** … 「IT の知識がゼロの人」と、使ってよいたとえの例
5. **章の背骨** … その章を貫く一本の考え方（例：セキュリティなら「見られたくない・書き換えられたくない・使えないと困る」）
6. **節の骨格** … ざっくり言うと → 本論 → まとめ → quiz。digest.ts が拾う書式なので崩されると困ると明記する
7. **記法の注意** … バックスラッシュのエスケープ、ヒアドキュメント禁止、`compare` は偶数個、図の中で `**` は効かない
8. **リンクしてよい節 id の全列挙** … これを省くと存在しない節へリンクして検査に落ちます
9. **間違えやすい事実の名指し** … 「公開鍵暗号は受信者の公開鍵で暗号化」のように、誤りやすい箇所を先回りで釘刺しする。**実際にこれが効いて、鍵の使い分けは全章で正しく書けていました**
10. **`npm run check` は実行させない** … 並行実行だとキャッシュが衝突するため。検査は依頼した側がまとめて 1 回やる

## 通しレビューのひな形

書いたものを検証させるプロンプトは [90-review.md](90-review.md) にあります。書くときとは要点が違います。

- **`--sandbox read-only` で走らせる。** レビューには指摘だけさせて、直すのは依頼した側。書き換えまで任せると、何が変わったのか追えなくなります
- **「自信がない箇所はありませんでした」を先回りで禁じる。** これを書かないと、毎回その報告が返ってきます。「確信度: 低」でもいいから必ず挙げさせること
- **間違いが多い箇所を名指しする。** 実際に効きました。法律の年数、公開鍵の使い分け、単位の換算、計算結果
- **範囲外のことまで指摘してくる。** プロンプトで「OSI 参照モデルの層と機器」と例示したら、ITパスポートの範囲外なのに「7 層がないのは重大」と報告されました。**こちらの例示がそのまま誘導になります。**採否は依頼した側が判断すること

直させるときは、**指摘をそのまま渡さず、採否を判断してから渡します。**「直す」「直さない（理由）」を分けて書いた指示にすると、余計な書き換えが減ります。

## Codex の利用上限に注意

5 本を並行で走らせたとき、3 本が**編集を終えた直後・報告を書く前**に利用上限に当たりました。ファイルは書き換わっているのに `-o` の出力が空、という状態になります。

- **`-o` の出力が空でも、ファイルは変わっていることがある。** `git diff` で必ず確かめる
- **何が済んで何が残ったかは、こちらで検算する。** 指示した用語を `grep -c` で数えるのが速いです
- 残りは自分で直せる分量のことが多いので、上限の回復を待つより手で埋めた方が早い場合があります

## 報告を鵜呑みにしないこと

Codex は毎回「事実に自信がない箇所はありません」と報告してきますが、**そのまま信用してはいけません。** 動作確認で章数を 15 → 12 と取り違えた例があります。

- 機械的な検査は `npm run check` で必ず確認する
- 内容の正しさは、**書いた人とは別の目**で通しレビューする（この方針の根拠は CLAUDE.md に書いてあります）
